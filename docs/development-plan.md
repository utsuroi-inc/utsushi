# 開発計画：巻物 / makimono

- 版：v0.1
- 作成日：2026-08-12
- 前提：Claude Code（Sonnet 5）による実装 + 人間による受け入れ検証
- 仕様の正：`docs/requirements.md`

---

## 1. この計画の考え方

### 1.1 なぜフェーズを分けるか

Chrome拡張は「ビルドしても、Chromeに読み込んで実際に撮ってみるまで正しさが分からない」種類のソフトウェアです。Claude Codeは `npm run build` の成否までは自分で確認できますが、**撮った画像が正しく繋がっているかは見られません**。つまり検証は人間がやるしかない。

したがってこの計画は、**「1フェーズ＝1回の人間検証で白黒がつく粒度」** で切ってあります。1フェーズを終えるたびにChromeで実際に撮り、通ればコミット、ダメなら同じセッション内で直す。フェーズをまたいで実装を進めると、どこで壊れたのか特定できなくなります。

### 1.2 Sonnet 5 での進め方

- **1セッション＝1フェーズ。** フェーズが通ったら `/clear` してコンテキストをリセットする。前フェーズの試行錯誤を引きずらせない
- **フェーズ1と3の冒頭はプランモード**（Shift+Tab を2回）で設計を先に出させ、合意してから実装に入る。この2つは設計判断が多く、いきなり書かせると手戻りが大きい
- **フェーズ0・4・5は直接実装で良い。** 定型作業なのでプランモードのコストが見合わない
- `docs/requirements.md` は毎セッション読ませる（CLAUDE.mdに明記済み）。ただし全文ではなく該当セクションを指定したほうが精度が上がる
- 詰まったら「なぜそうしたか説明して」と一度聞く。Sonnetは説明させると自分の誤りに気づいて直すことがある

### 1.3 コミット規律

フェーズごとに1コミット、メッセージは `feat(phase-N): 内容`。フェーズの途中で人間検証に落ちた場合はコミットしない。**動く状態でしかコミットしない**ことで、壊れたら直前のフェーズに戻れます。

## 2. 全体スケジュール

| フェーズ | 内容 | 想定セッション数 | 難度 | 累積の"動く度" |
|---|---|---|---|---|
| 0 | 雛形・ビルド環境 | 1 | 低 | 可視領域だけ撮れる |
| 1 | フルページ合成 | 1〜2 | **高** | 実用最小限（ここが山場） |
| 2 | 撮影品質 | 1〜2 | 中 | 実務で使える |
| 3 | エクスポート | 1〜2 | 中 | 一通り完成 |
| 4 | 仕上げ | 1〜2 | 低 | 人に渡せる |
| 5 | 堅牢化・ドキュメント | 1 | 低 | 配布できる |

**合計：6〜10セッション。** 集中して取れば2〜3日、週末に分けるなら2週間程度。

現実的な区切り方としては、**フェーズ0〜1を1日目**（ここを越えれば方式の妥当性が確定する）、**2〜3を2日目**、**4〜5を3日目**。フェーズ1が通った時点で「使えるツール」になるので、そこで一度止めて実務投入し、必要性を確かめてから先に進む判断もありです。

## 3. 事前準備（人間側・15分）

- [ ] Node.js 20以上を確認（`node -v`）
- [ ] 空のGitリポジトリを作成し、本パッケージ一式を配置してコミット
- [ ] Chromeで `chrome://extensions` を開き、デベロッパーモードをON
- [ ] 検証用サイトをブックマーク（下記）

**検証用サイト（固定して毎回同じものを使う）**

| 用途 | サイトの条件 | 例 |
|---|---|---|
| 基本 | 長い記事、固定要素なし | Wikipediaの長めの記事 |
| 固定ヘッダー | sticky/fixedヘッダーあり | 一般的なニュースサイト |
| lazy-load | 画像の遅延読込が多い | ECサイトのカテゴリ一覧 |
| 巨大 | 高さ3万px以上 | 長いドキュメントや無限スクロール系 |
| 自社 | 実務対象 | うつろいのサイト、たまな商店 |

毎回同じサイトで撮ることで、フェーズ間の劣化に気づけます。

## 4. フェーズ詳細

各フェーズは「キックオフプロンプト → 完了条件 → 人間の検証手順 → つまずきどころ」の構成です。

---

### フェーズ0：雛形とビルド環境

**目的**：ビルドしてChromeに読み込み、可視領域1枚だけ撮って新規タブに表示するところまで通す。配管を通すだけで、全ページ化はしない。

**キックオフプロンプト**
```
docs/requirements.md と CLAUDE.md を読んで、フェーズ0を実装して。

範囲：
- リポジトリ雛形（package.json, tsconfig, esbuildビルドスクリプト）
- manifest.json（MV3、permissions は activeTab / scripting / storage のみ）
- Service Worker：アイコンクリックで captureVisibleTab を1回だけ実行
- result.html：受け取った画像1枚を表示するだけ
- アイコンは単色の仮SVGから生成した仮画像でよい

全ページキャプチャ（スクロール＆スティッチ）はまだ実装しないこと。
完了したら、ビルド手順とChromeへの読み込み手順を教えて。
```

**完了条件**
- `npm run build` が成功し `dist/` が出力される
- `npm run typecheck` がエラーなし
- Chromeに読み込め、エラーが出ない

**人間の検証**
1. `npm run build`
2. `chrome://extensions` →「パッケージ化されていない拡張機能を読み込む」→ `dist/` を選択
3. 適当なページでツールバーアイコンをクリック
4. 新規タブが開き、**いま見えている範囲**の画像が表示される

**つまずきどころ**
- MV3のService Workerは非永続。グローバル変数に状態を持たせると消える。状態は `chrome.storage.session` かIndexedDBへ
- `activeTab` はユーザー操作起点でしか効かない。`chrome.action.onClicked` の中から使うこと

### フェーズ1：フルページ合成 ★最重要

**目的**：スクロールしながら撮り、正しく1枚に繋ぐ。このフェーズが通れば方式の妥当性が確定する。

**プランモードで先に確認すべき論点**（実装前にClaude Codeに答えさせる）
1. ページ高さの計測方法（`scrollHeight` / `offsetHeight` / `getBoundingClientRect` のどれをどう組み合わせるか）
2. DPRの扱い（キャプチャ画像は実ピクセル、スクロール量はCSSピクセル。この変換をどこで一元化するか）
3. 最下段の重複クロップの計算式
4. セグメントをService Workerから結果ページへ渡す方式（要件§6.3のIndexedDB案でよいか）
5. スクロール位置と注入CSSの復元をどう保証するか（try/finally構造）

**キックオフプロンプト**
```
プランモードで。docs/requirements.md の FR-02、§6.3、§6.4、NFR-05 を読んで、
フェーズ1（フルページのスクロール＆スティッチ）の実装計画を出して。

特に以下を明示すること：
1. 高さ計測の方法と、その選択理由
2. DPRとCSSピクセルの変換をどこで一元化するか
3. 最下段の重複クロップの計算式
4. セグメントの受け渡し方式
5. 異常終了時にスクロール位置と注入CSSを確実に戻す構造

計画に合意してから実装に入ること。
```

**完了条件**
- 受け入れ基準 #1（欠け・重複・ズレなく合成）と #3（DPR対応）を満たす
- キャプチャ後、ページのスクロール位置が元に戻る

**人間の検証**
1. Wikipediaの長い記事で撮る
2. 画像を等倍で開き、**繋ぎ目を上から順に目視**する。ズレ・重複・欠けがないか
3. 最下部が切れていないか、余分に重複していないか
4. 撮影後、元のページのスクロール位置が変わっていないか
5. 画像の実ピクセル幅が「ビューポート幅 × DPR」になっているか（Retinaなら2倍）

**つまずきどころ**
- **`captureVisibleTab` のレート制限（約2回/秒）**。ここを踏むと `MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND` エラーになる。待機600msは必須
- **DPRの二重適用**。CSSピクセルと実ピクセルの混同が、この方式で最も多いバグ。「スクロール量はCSS、キャンバスは実ピクセル」を境界で1回だけ変換する
- **`scroll-behavior: smooth`**。これを潰さないとスクロール完了前に撮ってしまう
- スクロール後の描画完了待ちは `setTimeout` だけに頼らず、`requestAnimationFrame` を2回挟むと安定する

**ここで一度立ち止まる**：フェーズ1が通れば実用最小限のツールとして使えます。実務で数回使ってみて、本当に先が必要か確かめてから2以降へ。

### フェーズ2：撮影品質

**目的**：実サイトで「使える画像」になるところまで詰める。固定ヘッダーの二重写りと、lazy-load画像の抜けを潰す。

**キックオフプロンプト**
```
docs/requirements.md の FR-03、FR-04、FR-05 を読んで、フェーズ2を実装して。

- 固定要素（fixed/sticky）の二重写り防止：1枚目には写し、2枚目以降は隠す。完了後に必ず復元
- lazy-load対策：loading="lazy" を eager にしてデコード完了を待つ
- 進捗表示：バッジ（%）とページ右下オーバーレイ。オーバーレイはキャプチャ瞬間に必ず非表示
- キャプチャ中の再クリックでキャンセル。キャンセル時もページ状態を完全復元

固定要素の走査は巨大DOMでのコストに注意すること。
```

**完了条件**：受け入れ基準 #2、#7、#8

**人間の検証**
1. 固定ヘッダーのあるニュースサイトで撮る → ヘッダーが**先頭に1回だけ**写っている
2. 画像多めのECカテゴリページで撮る → グレーのプレースホルダーが写っていない
3. 撮影中にオーバーレイが出て、**完成画像には写り込んでいない**
4. 撮影中に再クリック → 中断し、ページの見た目とスクロール位置が完全に元通り

**つまずきどころ**
- **オーバーレイの写り込み**。撮る直前に隠し、撮った直後に戻す順序制御。ここは高確率で一度失敗します
- **固定要素の復元漏れ**。元の `visibility` を保存してから変更すること。単に `visible` に戻すと、元から非表示だった要素が現れてしまう
- `sticky` は fixed と違い、位置によって挙動が変わる。過剰に隠すとコンテンツが欠けるので、検証は複数サイトで

### フェーズ3：エクスポート

**目的**：撮った画像を実際に持ち出せるようにする。PNG / JPEG / PDF / クリップボードの4経路。

**プランモードで確認すべき論点**
- PDFの寸法上限（1辺14,400pt）超過時の分割ロジック
- クリップボードAPIがユーザー操作起点を要求する制約への対応
- ファイル名テンプレートのサニタイズ範囲（Windows禁止文字 `\ / : * ? " < > |`）

**キックオフプロンプト**
```
プランモードで。docs/requirements.md の FR-06、FR-08、§12.4 を読んで、
フェーズ3（エクスポート）の計画を出して。

- PNG / JPEG（品質設定つき）/ クリップボードコピー / PDF
- PDFライブラリはローカルバンドル。MIT等の許諾的ライセンスに限る（§12.4）。
  採用候補とライセンスを提示してから決めること
- PDFは画像サイズ単一ページを既定とし、14,400pt超過時は自動分割
- ファイル名テンプレート {title}_{yyyyMMdd-HHmmss}、OS禁止文字はサニタイズ

licenses/ にライセンス全文を配置すること。
```

**完了条件**：受け入れ基準 #6

**人間の検証**
1. PNG / JPEG / PDF を保存し、それぞれ実際に開けるか確認
2. ファイル名がテンプレート通りか。**日本語タイトルのページ**でも壊れないか
3. クリップボードコピー後、Slackやドキュメントに貼れるか
4. 長いページのPDFが複数ページに正しく分割されているか
5. `licenses/` にライセンス全文があるか

**つまずきどころ**
- **クリップボードはユーザー操作（クリック）の同期的な流れの中でしか書けない**。await を挟むと権限を失うことがある
- 日本語ファイル名 + `<a download>` の組み合わせは環境差が出やすい。実際に保存して確かめる
- jsPDFに画像を渡す際、巨大なdataURLはメモリを食う。Blob経由を検討

### フェーズ4：仕上げ

**目的**：他人に渡せる状態にする。設定・ショートカット・多言語・巨大ページ対応。

**キックオフプロンプト**
```
docs/requirements.md の FR-07、FR-09、FR-10、FR-01（ショートカット）を読んで、
フェーズ4を実装して。

- 巨大ページの自動分割（高さ16,000実px上限、canvas面積上限も考慮）
- オプションページ（FR-09の表の全項目、chrome.storage.sync）
- キーボードショートカット Alt+Shift+P（commands API）
- i18n（_locales/ja, _locales/en、日本語が基準）

ハードコードされた文言が残っていないか最後に確認すること。
```

**完了条件**：受け入れ基準 #4、#9、#10

**人間の検証**
1. 高さ3万px級のページ → 自動分割され、「すべて保存」で全枚数落ちてくる
2. オプションを変更 → 実際に挙動が変わる（JPEG品質を0.5にして目に見えて劣化するか等）
3. `Alt+Shift+P` でアイコンクリックと同じ動作
4. Chromeの表示言語を英語に切り替え → UIが英語になる

**つまずきどころ**
- **Canvasの上限は高さだけでなく総面積**。幅が広いページでは16,000pxでも落ちる
- i18nは後付けするとハードコード文言が残る。grepで日本語リテラルを掃除する

## 5. リスクと対応

| リスク | 兆候 | 対応 |
|---|---|---|
| 繋ぎ目がどうしても合わない | 数px単位のズレが残る | DPR変換を1箇所に集約し直す。それでも駄目なら実測値（撮れた画像の実寸）を正として計算をやり直す |
| レート制限に頻繁に当たる | 撮影が途中で止まる | 待機を800msへ。それでも出るならリトライ回数を増やす |
| 巨大ページでブラウザが固まる | タブが応答しなくなる | 分割の閾値を下げる（16,000→8,000）。セグメントの破棄タイミングを見直す |
| フェーズ2以降で1の品質が劣化 | 前は撮れていたページで崩れる | 検証用サイトを固定しているので毎フェーズで気づける。直前フェーズのコミットに戻って差分を見る |
| Sonnetが仕様を先回りして作り込む | 頼んでいない機能が入る | プロンプトに「〜はまだ実装しない」を明示。CLAUDE.mdにも記載済み |

## 6. 完了の定義（Definition of Done）

以下がすべて満たされたらv1完成。

- [ ] 受け入れ基準 §9 の11項目すべてが手動検証で通る
- [ ] `npm run build` と `npm run typecheck` がエラーなし
- [ ] 権限が `activeTab` / `scripting` / `storage` に収まっている
- [ ] 外部通信ゼロをNetworkタブで確認済み
- [ ] `docs/requirements.md` §12（法務要件）の全項目を満たす
- [ ] READMEだけを見て第三者がインストールできる
- [ ] 実務のクライアント案件で1回以上、実際に使った

最後の1項目が実質的に一番重要です。作って満足せず、たまな商店なりFBMGなりの実案件で1回使ってから「完成」と呼ぶ。

## 7. v1完成後の判断ポイント

| 問い | Yesなら |
|---|---|
| 週に何度も使っているか | v2（注釈・トリミング）へ進む価値あり |
| クライアントに渡したい場面があったか | 配布形態を検討（unpacked配布 or ストア公開） |
| ストアに出すか | `docs/requirements.md` §12.5 のチェックリストを通し、プライバシーポリシーを整備 |
| 使っていないか | **そこで止める。** 作ったこと自体が学習で、無理に育てる必要はない |
