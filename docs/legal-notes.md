# 知財調査メモ：同種ツールの機能を独自実装することの適法性

- 調査日：2026-08-12
- 対象：フルページスクリーンショットChrome拡張の自作
- **免責：本メモは弁護士による法的助言ではなく、判断材料の整理です。** 有償配布や大規模公開に進む段階では、知財を扱う弁護士のレビューを受けてください。

---

## 結論

**機能が同じツールを自分で書く分には、著作権上の問題はほぼありません。** 実質的なリスクは著作権ではなく、①商標、②トレードドレス（look and feel）の側にあります。Chrome Web Storeの規約についても、調べた限り「同種の拡張が既にある」こと自体は障害になりません。

実装上の遵守事項は `docs/requirements.md` §12 に落としてあります。以下はその根拠。

---

## 1. 著作権 — 条件付きで問題なし

### 法的根拠

日本の著作権法10条3項は、プログラムの著作物に対する保護が **プログラム言語・規約・解法** に及ばないと定めています。

| 用語 | 定義（同項各号） | 具体例 |
|---|---|---|
| プログラム言語 | プログラムを表現する手段としての文字その他の記号及びその体系 | TypeScript, JavaScript |
| 規約 | 特定のプログラムにおけるプログラム言語の用法についての特別の約束 | インターフェース、通信プロトコル、API |
| 解法 | プログラムにおける電子計算機に対する指令の組合せの方法 | アルゴリズム |

したがって、最終的に実行される指令の内容（機能）が同一であっても、**指令の表現それ自体が異なれば著作権侵害にはあたりません**。解法はあくまで指令を出すためのアイデアであり、表現ではないためです。

「スクロールしながら可視領域を撮影し、繋ぎ合わせる」という処理方式そのものは解法＝保護対象外です。よって独自実装は適法。

### 条件

保護されるのは表現＝ソースコードと、アイコン等の素材です。したがって：

1. **他拡張のソースコードをコピーしない**
2. **他拡張のソースコードを読まない**（後述）
3. アイコン、スクリーンショット、イラスト、説明文などの素材を一切流用しない

### なぜ「読まない」ことが重要か

Chrome拡張はインストール時にローカルへ展開されるため、技術的にはソースを読めてしまいます。しかし著作権侵害の成立には「依拠性」（相手の著作物に依拠して作ったこと）が要件となり、**閲覧した事実はこの立証を容易にします**。

読まずに、公式ドキュメントと自前の仕様書だけから書けば、依拠性の議論そのものが生じません。これが `docs/requirements.md` §12.1 の意図です。

なお日本では2018年の著作権法改正で30条の4が整備され、表現の享受を目的としない利用（解析等）は広く許容される方向にあります。ただし相手方のEULAによる契約上の制限は別途残りえます。いずれにせよ「読まない」なら論点が発生しません。

## 2. 商標 — 最もはっきりした制約

`GOFULLPAGE` は **Full Page LLC** が保有する米国登録商標です（USPTOシリアル番号 90187286、2020年9月17日出願、2021年6月1日登録）。区分はコンピュータ・ソフトウェア製品／サービス。

さらに同社の利用規約は、**「Full Page」その他の名称・商標を、メタタグや隠しテキストに使用することを書面許可なく禁じています。**

### 遵守事項

- ツール名に `FullPage` / `Full Page` / `GoFullPage` を含めない
- ストア掲載情報（タイトル・説明・キーワード）に他社製品名を入れない
- 「○○の代替」「○○互換」といった比較表現も使わない（ストア審査とは別に商標的な火種になりうる）
- リポジトリ名・パッケージ名・内部名も統一して独自名称にする

**→ 本プロジェクトの名称を「写し / utsushi」としたのはこの要件を満たすためです。** 当初案の `fullpage-capture` は "FullPage" を含むため不採用としました。開発中は「巻物 / makimono」を用いていましたが、いずれも本節の要件を満たす独自名称です。

## 3. トレードドレス（look and feel）

Full Page LLCの利用規約は、ページヘッダー・カスタムグラフィック・ボタンアイコン・スクリプトを含むサービスの「look and feel」が同社のサービスマーク／商標／トレードドレスであり、書面許可なく全部または一部をコピー・模倣・使用してはならないと主張しています。

これは同社の主張であって、それがそのまま法的に通るかは別問題です。ただし争いを避ける意味で：

- アイコンのモチーフ・配色を寄せない（→ 和紙・写しのモチーフを採用）
- 結果ページのレイアウトを真似ない
- 進捗表示の見せ方も独自に決める

日本国内では **不正競争防止法**（周知表示混同惹起行為、商品形態模倣）が近い論点になります。ソフトウェアのUIに形態模倣規定がどこまで及ぶかは議論のあるところですが、「見た目で取り違えられうるか」を基準に避けておけば実務上まず問題になりません。

---

## 4. Chrome Web Store規約 — 意外と大丈夫

ここが調査で最も有益だった点です。

Googleの規約は「**同一の開発者・関連する開発者アカウント・その関係者**が、重複した体験や機能を提供する複数の拡張機能を提出すること」を禁じています。そして FAQ で、**無関係な開発者やpublisherによる競合拡張は重複コンテンツにあたらない** と明示されています。

つまり「同じことをする拡張が既に存在する」こと自体は、審査上の障害になりません。

### むしろ注意すべき条項

- **キーワードスパム**：誤解を招く／不適切な書式／非記述的／無関係／過剰／不適切なメタデータが禁止されている。対象には拡張の説明・開発者名・タイトル・アイコン・スクリーンショット・宣伝画像が含まれる。同一キーワードの反復は5回未満が目安
- **最小限の価値**：ブックマークや簡単なスクリプトで代替できる程度の拡張はスパム判定されうるとの指摘がある。本プロジェクトは該当しないが、説明文で価値を明確に述べること
- **単一目的（single purpose）**：拡張の目的が明確であること

配布前チェックリストは `docs/requirements.md` §12.5 に。

## 5. 特許 — 未調査

フルページキャプチャは先行技術が20年以上あるため、基本的な手法に有効な特許が生きている可能性は低いと見ていますが、**これは調査していません**。米国で商用展開する規模になった場合は別途調査の価値があります。

## 7. 差別化の方向（付随的な所見）

法務要件を満たすために独自性を出す必要がありますが、これは制約であると同時に設計の指針にもなります。

本プロジェクトが自然に持てる差別化点：

- **通信ゼロ・アカウント不要・テレメトリなし**（NFR-01）。競合の多くはSaaS化・アカウント化が進んでおり、「一切外に出さない」は監査業務のエビデンス取得という文脈で実質的な価値がある
- **権限が最小**（`activeTab` のみで `<all_urls>` を要求しない）。クライアント環境に入れてもらう際の説明が容易
- **日本語UIが第一級**。多くの競合は英語圏製で日本語は機械翻訳品質

ストア公開する場合、これらを説明文の中心に据えるのが、商標的にも審査的にも安全で、かつ正直な訴求になります。
